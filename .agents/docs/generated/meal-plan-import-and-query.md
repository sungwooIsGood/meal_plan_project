# 식단표 저장 · 조회 API 동작 문서

> 엑셀 식단표를 업로드하면 어떻게 메뉴가 추출·분류되어 DB에 저장되는지, 그리고 저장된
> 데이터를 어떻게 조회하는지를 설명한다. 실제 구현(코드) 기준 문서.

---

## 1. 한눈에 보는 전체 흐름

```
[사용자]
  │  ① 엑셀(.xlsx) 업로드
  ▼
POST /api/meal-plans/import
  │
  ├─ ② 엑셀 파싱 (Apache POI)         ← 셀의 모든 텍스트 추출
  │
  ├─ ③ 메뉴 분류 (AI 또는 규칙)        ← 7개 카테고리로 분류, 비메뉴는 제외
  │
  ├─ ④ 도메인 검증                    ← 분류된 메뉴 0개면 거부(422)
  │
  └─ ⑤ MongoDB 저장                  ← "업로드 1건 = 문서 1건"
  ▼
[응답] 201 Created + 분류 결과(JSON)

[나중에]
GET /api/meal-plans/{id}   → 저장된 식단표 1건 상세 조회
GET /api/meal-plans        → 저장된 식단표 목록(요약) 조회
```

---

## 2. 저장 API (Import)

### 요청
```
POST /api/meal-plans/import
Content-Type: multipart/form-data
form-field: file = <식단표.xlsx>
```

- **엑셀(.xlsx) 파일만** 허용한다. (구형 .xls 미지원)

### 처리 단계 (서버 내부)

1. **파싱 — 엑셀에서 글자 추출 (Apache POI)**
   - 모든 시트 → 모든 행 → 모든 셀을 순회하며 텍스트를 뽑는다.
   - 이 단계는 AI가 아니라 결정론적 라이브러리(POI)로 처리한다. (정확·무료·빠름)
   - 추출 결과는 "셀 텍스트 토큰 목록"이다. 예) `["월","화","흰쌀밥","미역국","콘푸로스트&우유/배추김치", ...]`

2. **분류 — 메뉴를 7개 카테고리로 나눔**
   - 합쳐진 셀(`"콘푸로스트&우유/배추김치"`)은 `/ & ,` 등으로 분리한다.
   - 각 메뉴를 아래 7개 카테고리 중 하나로 분류한다. **급식 메뉴가 아닌 토큰**(날짜·요일·헤더·학교명·알레르기번호 등)과 **양념류**(잼·버터·소스·드레싱)는 결과에서 **제외**한다.

   | 코드 | 분류 | 예시 |
   |---|---|---|
   | `STAPLE_FOOD` | 주식 | 흰쌀밥, 볶음밥, 국수, 모닝빵 |
   | `SOUP` | 국/탕 | 미역국, 된장찌개, 떡국, 돼지국밥 |
   | `MAIN_DISH` | 주찬(메인) | 제육볶음, 돈가스, 떡갈비 |
   | `SIDE_DISH` | 부찬(사이드) | 멸치볶음, 나물, 장조림, 전 |
   | `KIMCHI` | 김치 | 배추김치, 깍두기, 석박지 |
   | `DESSERT` | 후식 | 과일, 요거트, 떡 |
   | `BEVERAGE` | 음료 | 우유, 주스 |

   - 분류기는 두 가지 구현이 있고, 설정에 따라 선택된다:
     - **AI 분류기 (기본 권장)**: OpenAI 모델이 의미를 이해해 분류. `OPENAI_ENABLED=true` + API 키가 있을 때 동작.
     - **규칙 기반 분류기 (fallback)**: 키워드 매칭. AI가 꺼져 있거나 호출 실패 시 자동으로 사용. 외부 의존 없이 동작.

3. **도메인 검증**
   - 분류된 메뉴가 **하나도 없으면** "급식 식단표가 아니다"로 판단하여 거부한다. → `422`

4. **저장 — MongoDB**
   - "업로드 1건 = 문서(document) 1건"으로 저장한다.
   - 메뉴들은 문서 안에 **배열로 내장(embed)**된다. (별도 테이블/조인 없음)

### 저장 구조 (MongoDB `meal_plans` 컬렉션)
```json
{
  "_id": "c04c7c88-3452-4042-ae6d-02971277869b",   // 식단표 ID (UUID)
  "sourceFileName": "26년 조식 (게시).xlsx",          // 원본 파일명
  "importedAt": "2026-06-02T05:04:26.976Z",         // 저장 시각(UTC)
  "items": [                                        // 메뉴 배열
    { "name": "흰쌀밥",   "category": "STAPLE_FOOD" },
    { "name": "미역국",   "category": "SOUP" },
    { "name": "배추김치", "category": "KIMCHI" }
    // ... (분류된 메뉴 전부)
  ]
}
```
> 같은 메뉴가 여러 날 나오면 **중복도 그대로 저장**한다. (빈도 정보가 추천 단계에서 쓰이므로 저장 시 중복 제거하지 않음)

### 응답
- **201 Created** — 저장 성공
  ```json
  {
    "id": "c04c7c88-...",
    "sourceFileName": "26년 조식 (게시).xlsx",
    "importedAt": "2026-06-02T05:04:26.976Z",
    "totalItems": 325,
    "itemsByCategory": {
      "STAPLE_FOOD": ["흰쌀밥", "흑미밥", "..."],
      "SOUP": ["미역국", "된장찌개", "..."],
      "KIMCHI": ["배추김치", "..."],
      "BEVERAGE": ["우유"]
    }
  }
  ```
- **400 Bad Request** — 엑셀(.xlsx)이 아니거나 파일이 손상됨 (`error: INVALID_EXCEL_FILE`)
- **422 Unprocessable Entity** — 유효한 엑셀이지만 급식 내용이 아님(분류 가능한 메뉴 0개) (`error: NOT_MEAL_PLAN_CONTENT`)

### curl 예시
```bash
curl -i -F "file=@26년 조식 (게시).xlsx" http://localhost:8080/api/meal-plans/import
```

## 3. 조회 API (Query)

### 목록 조회 (요약)
```
GET /api/meal-plans
```
- 저장된 식단표들을 **import 최신순**으로, 요약 정보만 반환한다.
- 요약 = `id`, `sourceFileName`, `importedAt`, `totalItems` (메뉴 상세는 미포함).

```json
[
  {
    "id": "c04c7c88-...",
    "sourceFileName": "26년 조식 (게시).xlsx",
    "importedAt": "2026-06-02T05:04:26.976Z",
    "totalItems": 325
  }
]
```

```bash
curl -i http://localhost:8080/api/meal-plans
```

## 4. AI 분류는 어떤 규칙으로 동작하나 (프롬프트)

AI 분류기는 OpenAI 채팅 모델에게 **시스템 프롬프트(분류 규칙)** + **사용자 메시지(추출된 토큰 목록)**를 보내고,
정해진 JSON 형식으로만 답을 받는다. 호출 설정과 프롬프트 규칙은 아래와 같다.

### 호출 설정
- 모델: 설정값(`OPENAI_MODEL`, 기본 `gpt-5.5`)
- 응답 형식 강제: `response_format = json_object` (모델이 JSON 외 텍스트를 못 내도록)
- `temperature`: 설정된 경우에만 전송. gpt-5 계열은 비기본 temperature를 거부하므로 기본은 미전송(모델 기본값).
- 실패/키 없음 → 규칙 기반 분류기로 자동 fallback.

### 시스템 프롬프트에 담기는 규칙
프롬프트는 "급식 메뉴만 골라 7개 카테고리로 분류하고, 메뉴가 아닌 것은 제외하라"는 지시와 함께
아래 규칙들을 명시한다.

**(1) 메뉴가 아닌 것 — 결과에서 제외**
- 날짜, 요일(월~일), 숫자, 칼로리/영양정보, 알레르기 유발번호(예: `1.2.5.`), 비고
- 헤더/제목/학교명, 끼니명(조식·중식·석식), "식단표" 같은 표 라벨
- **양념·스프레드·소스·드레싱류**(잼·버터·시럽·케찹·마요네즈·소스·드레싱·양념장 등) — 곁들이는 부속이라 제외

**(2) 카테고리별 분류 기준 (경계 규칙 포함)**
| 코드 | 기준 | 핵심 경계 규칙 |
|---|---|---|
| `STAPLE_FOOD` 주식 | 탄수화물 중심(밥·면·빵·죽·필라프·리조또) | 모닝빵 같은 식사빵도 주식 |
| `SOUP` 국/탕 | 국물 요리(국·탕·찌개) | **국밥류(돼지국밥 등)는 밥이 들어가도 SOUP** |
| `MAIN_DISH` 주찬 | 그날의 주요리(고기·생선 메인) | 떡갈비 = 주찬 (후식 아님) |
| `SIDE_DISH` 부찬 | 보조 반찬 | **조림·장조림·무침·나물·전·튀김은 재료가 고기여도 부찬** |
| `KIMCHI` 김치 | 김치류만 | **김치 들어간 요리(김치볶음밥·김치찌개)는 김치 아님** |
| `DESSERT` 후식 | 과일·떡·떠먹는 빙과/요거트·디저트빵 | 떠먹는 요거트는 후식 |
| `BEVERAGE` 음료 | 마시는 것(우유·주스·차·탄산) | 마시는 요구르트는 음료 |

**(3) 경계 판단 원칙**
- 애매하면 **"어떻게 먹는가"**로 판단: 마시면 음료, 떠먹으면 후식, 밥에 곁들이는 작은 반찬이면 부찬.
- 한 셀에 여러 메뉴가 `/`·`&`로 묶여 있으면 각각 분리해 분류.

**(4) 출력 형식 (고정)**
```json
{"items":[{"name":"메뉴명","category":"CATEGORY_CODE"}]}
```
- 설명·주석 없이 이 JSON만. 급식 메뉴가 하나도 없으면 `{"items":[]}`.

### 환각(없는 메뉴 생성) 방지
- 모델 응답을 그대로 믿지 않는다. 분류 결과 중 **카테고리 코드가 7종에 없거나 이름이 빈 항목은 버린다.**
- 즉 프롬프트로 형식을 강제하고, 코드에서 한 번 더 검증해서 잘못된 항목을 걸러낸다.

### 규칙 기반 분류기 (AI 미사용 시)
AI가 꺼져 있거나 호출 실패 시 사용하는 fallback. 위 의미 규칙 대신 **키워드 매칭**으로 분류한다.
- 카테고리별 키워드 목록을 우선순위 순서로 검사해 먼저 매칭되는 카테고리로 분류.
- 한계: 의미가 아니라 글자 포함이라 오분류 가능(예: "떡갈비"의 "떡" → 후식으로 잘못 분류). 정확도가 필요하면 AI 사용 권장.

## 5. 자주 묻는 점

- **"문서 1개"가 메뉴 1개라는 뜻인가?**
  아니다. 문서 1개 = 엑셀 파일 1건이고, 그 문서 안의 `items` 배열에 메뉴 여러 개(예: 325개)가 담긴다.
  엑셀을 2개 올리면 문서가 2개가 된다.

- **왜 RDBMS가 아니라 MongoDB(문서형)인가?**
  "업로드 1건"을 통째로 읽고 쓰는 패턴이고, 카테고리별 메뉴 개수가 가변적이라 join 없는 문서 모델이 적합하다.

- **AI를 안 켜면 동작 안 하나?**
  동작한다. AI가 꺼져 있으면 규칙 기반 분류기로 자동 처리된다. 다만 의미 기반이 아니라 키워드 매칭이라
  정확도가 낮다(예: "떡갈비"의 "떡" 때문에 후식으로 오분류). 정확한 분류는 AI 사용을 권장한다.

- **엑셀 파싱도 AI가 하나?**
  아니다. 글자 추출은 Apache POI(결정론적)로 한다. AI는 추출된 텍스트를 "분류"하는 데만 쓰인다.
```
